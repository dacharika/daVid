# render cache is poisoned by a partial write: a crashed melt leaves a truncated mp4 the next resumed run returns as done
renderCmd (cmd/cutvec/main.go:1357,1364) passes the FINAL cache path out := proj.RenderPath(hash,quality) straight to the melt worker as its "output" param, so melt streams the encoded video into the cache location itself. If melt dies mid-encode (SIGKILL/crash/disk-full/melt error after it has opened the output), a truncated .mp4 is left at that cache path. On worker error renderCmd returns at main.go:1367-1369 WITHOUT removing the partial out. HasRender (internal/project/project.go:581-584) is a bare os.Stat existence check, so the next resumed run hits the cache-hit branch (main.go:1332-1340), returns Cached:true pointing at the corrupt/truncated file, and never re-renders — the 'deterministic idempotent resumable steps' promise is broken exactly after the crash resumability exists for, on the longest/most expensive step. CONTRAST proving this is render-specific: every other worker-backed step has the worker RETURN its result to Go and Go writes the cache AFTER full success — transcribe (main.go:590-597: transcriptFromResult then WriteTranscript only after Invoke returns nil), and likewise index/speakers — so a mid-run failure writes no cache entry and the step re-runs cleanly. Render is the ONLY step whose worker writes directly to the cache path, so it is the only one vulnerable to partial-write cache poisoning. LATENT/GREEN: TestRenderCacheHitIdempotent (cmd/cutvec/main_test.go:1179) only covers the happy path (successful render, then a re-run with a nonexistent worker proves the hit); no test covers a worker that writes partial output then exits non-zero, so the poisoning ships green. UNIT-TESTABLE with no real melt: the existing fake render worker (main_test.go:114-128) already writes to req.Params[output]; a 'render-partial' mode that writes a few bytes then os.Exit(1) simulates a crashed encode, after which a second render call returning Cached:true at the truncated path demonstrates the bug. FIX: publish atomically — render to a temp path (e.g. out+".tmp") and os.Rename into place only after the worker returns success, OR os.Remove(out) on worker error, OR make HasRender validate completeness. Write-to-temp-then-rename mirrors the all-or-nothing guarantee the JSON caches already get for free. Distinct from open 029 (hook/caption overlap), 030 (audio gain), 031 (multi-clip sequencing), 032 (blank element) and from done 017 (render happy path).
